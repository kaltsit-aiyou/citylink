# CityLink 开发问题与排错记录

- 文档版本：V0.1
- 对应项目蓝图：阶段 0～1 的准备、工程搭建和账户功能
- 记录日期：2026-11-25
- 记录原则：区分**真正的构建或运行错误**、**IDEA 编辑器提示**和**工具自身的警告**。有些历史截图没有包含第一条根因日志，对这些问题只记录已证实的现象和有效排查方法，不猜测唯一原因。
- 更新原则：阶段开发中先记下新问题；阶段验收时补齐原因、修复、验证结果，再统一更新本文件。

## 1. 下次遇错先按这条顺序排查

1. **记录预期和实际结果**：执行了什么操作、期望什么、实际看到什么。
2. **确定出错层次**：IDEA 提示、Maven 构建、Java 启动、数据库、HTTP 接口、浏览器页面，还是 Git 网络。
3. **找第一条有用的错误**：保存完整日志，不只截取最末尾的异常类名。
4. **做一个独立验证**：例如 IDE 显示红色时，运行 Maven `test`；页面出错时，查看浏览器“网络”面板的实际状态码。
5. **每次只改一个可能原因**：改完重新运行同一个验证步骤，记录结果。
6. **区分“已解决”和“尚未确认根因”**：能运行不代表之前每条警告都已解释清楚。

## 2. Maven、IDEA 与 Java 环境

| 遇到的现象 | 当时如何理解和处理 | 以后怎么判断 |
| --- | --- | --- |
| IDEA Maven 同步出现 `Unable to create injector`、`Guice/MissingImplementation` | 截图主要是异常尾部，不能凭这几个词认定 `pom.xml` 写错。随后分别检查 IDEA 的 Maven 主路径、Wrapper 配置、依赖仓库访问，并运行 Maven `test`；后续测试得到 `BUILD SUCCESS`。**原同步异常的唯一根因没有被完整日志证明。** | 保存同步日志的第一条错误；比较“IDEA 导入失败”和“命令行构建失败”是否同时存在。 |
| `spring-boot-starter-parent:4.1.2`、validation 依赖在 IDEA 中标红 | IDEA 当时未正确解析所需依赖；后来依赖能够下载，Maven 测试成功，重新加载 Maven 项目后编辑器恢复。 | 先核对坐标、版本、仓库连通和 Maven 是否处于离线模式；在 IDEA 右侧 Maven 窗口点“重新加载所有 Maven 项目”，再用真实构建结果判断。 |
| 分不清“已捆绑 Maven 3”和“Maven 包装器” | IDEA 自带的 Maven 与项目的 Maven Wrapper 都能运行 Maven；Wrapper 的 `distributionUrl` 指向项目约定的 Maven 3.9.16。`wrapperVersion=3.3.4` 不是 Maven 主程序版本。 | 团队希望构建工具版本一致时优先使用项目 Wrapper；IDEA 中的选择要与实际运行日志核对。 |
| 测试日志出现 Jansi、`Unsafe`、Mockito 动态 agent、JVM Sharing 警告 | 这些是工具或运行时兼容性提示；出现它们时，测试仍曾显示 `Tests run: 2, Failures: 0, Errors: 0` 和 `BUILD SUCCESS`。一次日志使用 Java 26，项目配置的目标版本是 Java 17。 | 先看测试结果，再处理警告；在 IDEA 的项目 SDK 和 Maven Runner 中尽量使用预定的 Java 17，避免运行时版本混乱。未来升级工具时再复核仍存在的警告。 |
| `@SpringBootTest` 输出“Could not detect default configuration classes” | 同一日志随后找到 `BackendApplication`，应用启动且测试通过；这条信息不是本次失败原因。 | 看完整上下文，尤其是最后的测试结果，不要只看到 `Could not` 就认定测试失败。 |
| IDEA 将 SQL 文件顶部标黄，提示未配置 SQL 方言 | SQL 编辑器无法按特定数据库提供准确的语法提示；不等于 MySQL 执行失败。 | 在提示条选择“使用 MySQL”。是否建表成功以 MySQL 执行结果为准。 |
| `application.properties` 中的中文注释出现 `ISO-8859-1` 字符警告 | 这是文件编码和编辑器检查问题，与依赖红色、数据库连接失败不是同一类故障；本阶段测试通过，但不能据此断言所有编辑器警告都已消失。 | 核对 IDEA 的“文件 → 设置 → 编辑器 → 文件编码”以及文件实际编码；修改编码后重新运行应用测试。也可将该文件的说明改用 ASCII 注释。不要把真实密码写入配置文件。 |
| 依赖安全扫描显示黄色 CVE 提示 | 扫描提示依赖可能有已公布的风险，不是“找不到依赖”，也不直接等于编译失败。 | 先确认是直接依赖还是传递依赖、实际版本和适用条件，再规划兼容的升级并运行测试；不要为了消掉黄色提示盲目改版本。 |

## 3. MySQL、SQL 和 Java 包结构

### 3.1 数据库服务、登录与环境变量

曾确认 Windows 服务 `MySQL80` 为 `Running`，并通过 MySQL 命令行看到服务器版本和当前用户。`Running` 只说明服务在运行；应用要成功查询，还需要数据库 `citylink`、表 `app_user`、应用账号及密码配置都正确。

项目配置使用专门的 `citylink_app` 账号，并从 `CITYLINK_DB_PASSWORD` 读取密码；JWT 密钥从 `CITYLINK_JWT_SECRET` 读取。这样可以避免把真实凭据提交到 Git。MySQL 管理员 `root` 的密码与应用账号密码是两个概念。

以后先按顺序检查：**MySQL 服务 → 能否用应用账号连接 → 数据库与表 → 环境变量 → 后端日志**。电脑重启后可先在 PowerShell 用 `Get-Service MySQL80` 查看状态；只有服务未运行时才需要启动它。

### 3.2 `Database changed` 与 `show tables`

在 MySQL 中执行 `USE citylink;` 后出现 `Database changed`，意思是**当前操作的数据库已切换**，不是报错。创建 `app_user` 后看到 `Query OK`，说明建表语句成功。

曾输入 `show tables` 却没有输入分号，命令行出现 `->`：MySQL 正在等待这一条语句结束。随后又输入一遍，两个片段被当成同一条 SQL，产生语法错误。正确输入是：

```sql
SHOW TABLES;
```

看到 `app_user` 才是验证表存在的结果。遇到 `->` 时先检查分号、引号和括号是否未闭合，不要不断重复整条语句。

### 3.3 Java 包与 MyBatis 导入标红

创建 `UserMapper` 时曾出现 `package user;`，但文件应处在 `io.github.kaltsitaiyou.citylink.user` 包内。修改包声明并确保它位于 `BackendApplication` 的扫描范围内后，包结构才一致。

`Mapper`、`Select` 无法解析时，还要检查 `pom.xml` 是否包含 MyBatis Starter、Maven 是否已成功加载依赖，以及 `@Mapper` 是否导入正确。**刷新 IDEA 文件树**和**重新加载 Maven 依赖**不是同一个动作；依赖问题要检查 Maven 工具窗口和构建结果。

### 3.4 找不到 `UserService` Bean

IDEA 曾提示 `AuthController` 构造方法无法注入 `UserService`。当前可工作的代码中，`UserService` 位于启动类包的子包，并标记 `@Service`。这说明 Spring 需要在扫描范围内找到可管理的业务对象。

以后按顺序检查：类文件是否存在 → 包声明是否正确 → 是否有 `@Service` → 是否处在启动类扫描范围 → Maven 构建与应用启动日志。历史截图不能单独证明当时只有一个原因；修复后以应用能启动、接口能调用为验证。

## 4. HTTP、登录、页面与中文乱码

| 遇到的现象 | 处理与认识 | 验证方式 |
| --- | --- | --- |
| 浏览器访问 `localhost:8080` 显示“连接被拒绝” | 当时没有正在该端口提供页面的后端服务；后来前端页面放入 Spring Boot 的 `static` 目录。 | 先在 IDEA 启动 `BackendApplication`，看到 `Started BackendApplication` 后再访问地址。不能通过双击 HTML 的 `file:` 地址验证当前接口交互。 |
| 注册、登录或其他请求错误地都显示 401 | 检查安全规则顺序：允许匿名访问的首页、静态资源、注册与登录规则必须在 `.anyRequest().authenticated()` 之前；还需留意错误分发产生的响应。当前 `SecurityConfig` 已将相关放行规则放在前面。 | 分别验证合法注册、重复注册、错误密码登录、无令牌访问资料、携带令牌访问资料，比较各自的 HTTP 状态。 |
| 修改中文昵称后显示 `????` 或乱码 | 请求发送和响应读取是两个独立的编码环节。曾先将中文 JSON 明确编码为 UTF-8 字节发送，再用按 UTF-8 解码响应的客户端读取，最终读到正确中文。 | 修改后重新 GET 资料；必要时查看数据库中的值。不要仅凭 PowerShell 控制台显示，就判断数据库内容一定坏了。 |
| PowerShell `Invoke-WebRequest` 对无令牌 GET 报 `ProtocolViolationException` | 这是客户端工具解析响应时出现的异常，不能直接把它解释为后端业务状态码。 | 换用能显示原始响应状态的工具（例如 `curl.exe -i`），同时看后端日志和浏览器“网络”面板。 |
| 点击“保存修改”后资料区域更新 | 页面调用 `PUT /api/users/me`，收到新资料后更新显示；出现“资料已保存”是成功提示。 | 手动按 F5，确认昵称仍在，再退出登录；如果出现真正的整页白屏重载，则单独排查。 |

页面使用 `sessionStorage` 保存当前标签页的令牌，不保存用户密码。退出登录会清除前端令牌和显示资料；后端尚未实现服务端撤销令牌，这属于功能边界，不是本次“退出按钮失效”。

## 5. Git、GitHub 与提交过程

| 遇到的现象 | 原因或处理 | 下次记住 |
| --- | --- | --- |
| `git status` 说工作区干净，但 `git status --short --untracked-files=all` 又列出 `?? backend/...` | `??` 表示此前尚未纳入版本控制的文件；需要核对运行命令所在仓库及当时状态，不能只凭一句“干净”推断新文件已提交。 | 在项目根目录查看完整状态与未跟踪文件，再决定 `git add` 的范围。 |
| `git add` 后出现 `LF will be replaced by CRLF` | Git 在 Windows 工作区提示将来可能调整行尾格式；这是警告，不表示暂存失败。 | 继续查看 `git status` 和暂存内容；不要因这条警告重复添加或随意重写文件。 |
| `git diff --cached --check` 报文档行尾空白 | 已暂存的 Markdown 行末有多余空格。删除多余空格后，重新 `git add` 相应文档，再运行检查；后来检查已不再报错。 | 提交前检查暂存内容，而不只看工作区文件。 |
| `git push` 出现连接重置或无法连接 GitHub | 浏览器能打开 GitHub、TCP 443 测试成功，只能说明部分网络环节可用，不保证 Git 的 HTTPS 请求、代理或认证流程一定成功。后来手动推送成功。 | 本地提交不会因推送失败而消失；先看 `git status -sb` 是否 `ahead 1`，检查连接和认证后再重试。不要用强制推送处理网络问题。 |
| 自动环境推送时凭据工具无法启动 | 这是推送环境的凭据调用问题；本地提交已经创建，用户随后在自己的 PowerShell 完成推送。 | `commit` 与 `push` 是两步：已有本地提交时只需推送，不要为同一批内容重复提交。 |
| 不清楚 `origin main` 和单独 `git push` 的区别 | `origin` 是远程仓库简称，`main` 是分支。当前分支关联 `origin/main` 后，直接 `git push` 也能推到对应位置。 | 用 `git status -sb` 检查是否仍显示 `ahead`，确认本地与远程是否同步。 |

本项目约定**完成一个项目阶段再集中整理文档和提交**。修复一次 Maven 提示或改一行注释，都不需要单独提高项目文档版本号。

## 6. 本阶段的已知边界

- 现有两个 Maven 测试覆盖应用启动和数据库查询；注册、登录、权限等分支主要完成了人工接口和浏览器联调，后续可补充更有针对性的自动化测试。
- IDEA 的编码提示、依赖安全扫描提示与“项目能运行”是不同问题，不能互相代替结论。
- 当前页面只支持填写头像图片网址，没有实现图片上传。
- 当前退出登录只清除客户端保存的令牌，没有服务端令牌撤销。
- 商户、笔记、关注、圈子等属于后续阶段，不能写成本阶段已解决的问题。

## 7. 每个新阶段如何更新本记录

阶段结束时新增一个小节，按以下格式填写：

| 项目 | 要记录的内容 |
| --- | --- |
| 阶段与日期 | 原项目蓝图编号、阶段名称、验收日期 |
| 功能范围 | 本阶段实际完成的接口、页面、数据库表 |
| 新问题 | 原始报错或截图中的关键文字、出现条件 |
| 原因与证据 | 已证实的原因；若未查明，明确写“未确认” |
| 解决步骤 | 改了什么，为什么这样改 |
| 验证 | 哪条测试、哪个接口或哪个页面操作证明已解决 |
| 后续注意 | 仍存在的警告、功能边界或下一阶段任务 |

问题可以在开发时随手记；**文档版本和正式总结在阶段完成时统一更新**。这样既能保留排错经过，也不会因为每次小修复而频繁改版本。
